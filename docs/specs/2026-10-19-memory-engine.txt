# Chairman OS — Universal Capture & AI Memory Engine

## 0. 프로젝트 목적

기존 Chairman OS에 **Universal Capture & AI Memory Engine**을 신규 개발한다.

이 시스템은 대표가 언제 어디서든 작성한 메모, 미팅 기록, 음성, 화상회의, 전화, 메시지, 이메일, 파일 등을 AI가 분석해 기존 Chairman OS 데이터베이스와 연결하는 시스템이다.

단순한 AI 메모장, 회의록 작성 프로그램 또는 업무 관리 앱을 만드는 것이 아니다.

**궁극적인 목표는 Chairman OS가 대표의 모든 사업 관련 대화와 생각을 시간순으로 기억하고, 새로운 정보가 들어올 때마다 기존 기억과 비교해 변화, 결정, 약속, 리스크, 기회를 발견하는 것이다.**

핵심 철학:

> Capture Everything → Understand Everything → Connect Everything → Remember Everything → Support Better Decisions.

사용자는 정보를 입력할 때 반드시 회사, 프로젝트, 사람을 직접 지정할 필요가 없어야 한다.

AI가 자동으로 분류하고, 기존 DB와 연결하되 불확실한 연결은 사용자에게 확인받는다.

기존 Chairman OS의 그룹 관제탑 구조, Company, People, Project, Decision, Task, Dashboard 등은 유지한다.

# 2. 핵심 기능 — Universal Capture

## 2.1 Global Quick Capture

Chairman OS의 모든 화면에서 사용할 수 있는 고정형 Quick Capture 기능을 개발한다.

Desktop:
- 화면 우측 하단 또는 기존 UI에 자연스럽게 통합된 Quick Capture 버튼
- 클릭 시 Modal 또는 Side Panel
- 키보드 단축키 지원
- 입력 중 작성 내용 자동 보존

Mobile:
- 하단에서 열리는 Capture 인터페이스
- 모바일 화면과 터치 조작 최적화
- 음성 녹음 시작까지 최소한의 조작
- 입력 도중 화면 전환 시 내용 보존

입력 유형:

1. Quick Note — 텍스트 메모
2. Voice Note — 음성 메모
3. Meeting — 대면회의, 텍스트 기반 회의 기록
4. Online Meeting — 화상회의 기록
5. File — PDF, Word, Excel, PPT, 이미지 등
6. Conversation — 카카오톡, WhatsApp 등 대화 내보내기 자료
7. Email — 이메일 데이터
8. Phone Call — 합법적으로 확보한 통화 녹음 파일

모든 입력은 공통 Capture 엔진으로 전달한다.

처음에는 텍스트, 음성파일, 일반 문서, 기본 Meeting 기능을 실제로 구현한다.

외부 화상회의·메신저·이메일 자동 연동은 후속 단계로 분리하되, 데이터 구조는 처음부터 확장 가능하게 설계한다.

## 2.2 Capture 입력 UI

텍스트 입력 화면은 가능한 한 단순하게 만든다.

기본 구성:
- 큰 자유 입력창
- Voice 버튼
- Attachment 버튼
- Meeting 시작 버튼
- 저장 상태 표시
- AI 분석 상태 표시

예시:

"오늘 베트남 방 사장과 이야기했다. SB 고객 관리 담당자를 다시 정해야 하고, 이 부장이 방문한 뒤 결정하기로 했다."

사용자가 이를 입력하면:

1. 원본을 즉시 저장한다.
2. AI 분석 작업을 등록한다.
3. 기존 회사·인물·프로젝트를 검색한다.
4. 관련 기억과 연결한다.
5. 결과를 사용자에게 보여준다.

**사용자가 AI 분석 완료를 기다리지 않아도 원본 메모가 보존되어야 한다.**

# 3. Meeting Workspace

회의를 별도로 관리할 수 있는 Meeting Workspace를 개발한다.

회의 생성 방식:
- 즉시 시작
- 제목을 정하고 시작
- 이전 일정과 연결
- 녹음 없이 회의 메모만 작성

회의 화면 구성:

### Header
- Meeting Title
- Date / Time
- Participants
- Related Company
- Related Project
- Recording Status

### Workspace
- Live Notes
- Audio Recording
- Transcript
- Attachments
- AI Summary

### 종료 후 AI 결과
- Executive Summary
- Key Discussions
- Decisions
- Commitments
- Action Items
- Risks
- Open Questions
- Related Historical Context

하나의 Meeting ID에 여러 데이터가 동시에 연결되어야 한다.

예를 들어:
- 회의 중 작성한 메모
- 녹음 원본
- 음성 전사
- 첨부한 계약서
- 회의 참석자
- AI 분석 결과

이 데이터들을 각각 다른 미팅처럼 취급하지 않는다.

녹음 중에도 메모를 자유롭게 작성하도록 한다.

가능한 경우 메모 작성 시점과 녹음 시점을 매칭한다.

음성 전사에서는 발언자를 구분할 수 있도록 확장 가능한 구조를 사용한다.

발언자가 불확실하면 Speaker 1, Speaker 2 등으로 표시하고 임의로 특정 인물과 연결하지 않는다.

브라우저나 모바일 OS의 백그라운드 녹음 제한이 있을 수 있으므로 녹음 중단·권한 오류·네트워크 장애를 명확하게 처리한다.

회의 참여자 고지 및 녹음 동의가 필요한 환경을 고려한 UI를 설계한다.

# 4. AI Memory Processing Engine

AI 처리 과정은 독립적인 파이프라인으로 개발한다.

## Step 1 — Ingestion

원본 데이터를 저장한다.

저장 대상:
- Raw Text
- Audio File
- Transcript
- File Reference
- Source Type
- Created At
- Capture Time
- User ID
- Source Metadata

음성은 Speech-to-Text 엔진으로 텍스트화한다.

파일은 형식별 Extractor를 이용한다.

원본, 변환된 텍스트, AI 생성 결과를 서로 구별해 저장한다.

## Step 2 — Classification

AI가 내용을 분류한다.

주요 분류:
- Business Meeting
- Investment / M&A
- Operations
- Sales
- Finance
- R&D
- HR
- Personal Note
- Idea
- Strategy
- Other

하나의 기록이 여러 유형에 속할 수 있다.

유형 분류와 회사·프로젝트 연결은 서로 독립적으로 처리한다.

## Step 3 — Entity Extraction

다음 엔티티를 추출한다.

- Person
- Company
- Project
- Product
- Location
- Financial Amount
- Date
- Deadline
- Agreement
- Contract
- Other Relevant Entity

기존 DB에 같은 인물·회사가 있는지 검색한다.

한국어·영어 이름, 약칭, 별칭, 직함을 지원한다.

예:
- Mr. Bang / 방 사장
- DY Vietnam / DY Industrial Vietnam
- 보람 / 보람씨앤에이치

단, 같은 이름이나 직함이라고 해서 무조건 동일 인물로 합치지 않는다.

신원 확인이 어려운 경우 Pending Entity로 관리한다.

## Step 4 — Knowledge Extraction

각 메모와 미팅에서 다음 정보를 구조화한다.

**FACT**
객관적으로 확인되거나 문서에서 추출된 사실

**CLAIM**
특정 인물이 주장하거나 설명한 내용

**DECISION**
확정된 의사결정

**PROPOSAL**
아직 확정되지 않은 제안

**COMMITMENT**
누군가가 이행하겠다고 약속한 내용

**TASK**
구체적 실행이 필요한 업무

**RISK**
사업, 계약, 자금, 일정 등에 영향을 줄 수 있는 위험

**OPPORTUNITY**
새로운 사업 기회 및 아이디어

**QUESTION**
아직 확인되지 않은 사항

각 항목은 가능하면 다음 메타데이터를 포함한다.

- Content
- Type
- Source Capture ID
- Source Segment / Timestamp
- Speaker
- Related Entities
- Event Time
- Recorded Time
- Confidence
- Verification Status
- Current Status

정보가 없을 때 AI가 담당자, 금액, 기한을 임의로 만들어내서는 안 된다.

상대방의 발언은 객관적으로 입증된 사실과 구별한다.

## Step 5 — Context Retrieval

새 정보와 관련된 기존 기록을 검색한다.

우선순위:
1. 직접 연결된 회사·프로젝트
2. 동일 인물
3. 기존 약속과 실행 업무
4. 진행 중인 결정
5. 의미가 유사한 과거 기록

단순 텍스트 검색뿐 아니라 Semantic Search를 사용한다.

PostgreSQL Full Text Search와 Vector Search를 결합하는 Hybrid Search를 권장한다.

## Step 6 — Conflict & Change Detection

새 기록과 기존 기록을 비교한다.

감지할 변화:
- 금액 변경
- 납기 변경
- 담당자 변경
- 투자 조건 변경
- 약속 내용 변경
- 결정의 취소 또는 수정
- 이전 발언과 상충하는 새로운 발언
- 반복되는 일정 지연

예시:

과거 기록:
"11월까지 납품하기로 약속"

새로운 기록:
"12월까지 납품 가능"

AI 결과:
"납품 예정 시점이 11월에서 12월로 변경된 것으로 보입니다. 변경 확정 여부를 확인해야 합니다."

반드시 관련 원본 기록으로 이동할 수 있어야 한다.

서로 모순되는 주장을 AI가 임의로 해결해서는 안 된다.

## Step 7 — Memory Update

AI 분석 결과를 기존 DB와 연결한다.

저장 정책:

- 원본 기록: 즉시 저장
- AI 추출 정보: 초안 상태로 저장 가능
- 신뢰도가 충분한 비파괴적 연결: 정책에 따라 자동 등록
- 주요 결정사항: 기존 기록의 확정 여부 확인
- 재무 수치나 투자 조건 변경: 사용자 승인 필요
- 기존 확정 사실과 충돌: Review Queue 등록

기존 사실을 수정할 때 원본 정보를 삭제하거나 덮어쓰지 않는다.

변경 이력과 증거를 남긴다.

# 7. Ask Chairman AI

전체 메모와 사업 기록에 자연어로 질문하는 인터페이스를 개발한다.

예시 질문:

"지난 3개월 동안 베트남 법인에서 논의한 인사 문제를 정리해줘."

"이너시아와 지금까지 약속한 내용은 뭐야?"

"내가 투자금 관련해서 결정하지 못한 것은 무엇이지?"

"지난 미팅과 오늘 미팅에서 달라진 것은?"

"최근 한 달간 내가 지시한 업무 중 완료되지 않은 것은?"

"특정 업체가 반복해서 납기를 변경한 적이 있어?"

답변 생성 원칙:

1. 관련 데이터 검색
2. 사용자 권한 검증
3. 시간순 정렬 및 증거 대조
4. AI 답변 생성
5. 관련 원본 출처 표시
6. 확실하지 않은 내용은 불확실하다고 명시

모든 답변은 가능한 범위에서 원본 메모나 미팅으로 연결한다.

검색되지 않는 내용을 지어내지 않는다.

검색 범위, 날짜, 관련 회사도 사용자에게 이해하기 쉽게 표시한다.

문서나 회의 내용 안에 포함된 악의적인 지시는 AI 시스템 명령으로 실행하지 않는다.

# 8. Follow-up & Commitment Engine

AI가 메모에서 추출한 약속과 실행 업무를 관리한다.

다음 두 가지를 반드시 구분한다.

**My Commitments**
내가 다른 사람에게 약속한 일

**Others' Commitments**
다른 사람이 나에게 약속한 일

각 약속은 다음 속성을 가진다.

- Who
- Promised To
- What
- Due Date
- Related Company / Project
- Source Meeting
- Status
- Last Update

기존 Chairman OS Task 구조가 있다면 그것을 사용한다.

동일한 약속이 여러 회의에서 언급되었다면 중복 업무를 생성하지 않는다.

새로 확인된 진행 상황만 추가한다.

기한이 없으면 AI가 날짜를 임의로 설정하지 않는다.

"다음 주", "이번 금요일" 등의 상대 날짜는 실제 기록 시점과 시간대를 기준으로 해석한다.

모호한 날짜는 사용자의 확인을 요청한다.

장기적으로 가장 중요한 기능이다.

새로운 Memory가 쌓일 때 기존 기록과 비교해 대표가 놓칠 수 있는 중요한 사항을 발견한다.

- Overdue Commitments
- Unresolved Decisions
- Conflicting Information
- Repeated Delays
- Financial Exposure
- Key Relationship Changes
- High-priority Opportunities

중요도 등급:
- Critical
- High
- Medium
- Low

단순히 모든 미완료 업무를 경고하지 않는다.

실질적으로 사업적 중요성이 높은 것부터 제안한다.

기존 Chairman Dashboard에 Attention 섹션을 연결한다.

모든 경고에는 근거, 관련 프로젝트, 미팅 기록을 표시한다.

AI의 추정과 확정 사실을 구별한다.

MVP에서는 기본 위험 후보 탐지와 Review UI를 우선 구현하고, 고급 자동 분석은 후속 단계로 확장한다.

# 14. 필수 테스트 시나리오

아래 테스트 케이스를 구현한다.

### Case A — 자유 메모

입력:
"오늘 베트남 법인 영업 상황을 점검했다. SB 고객 8개사 관리 담당자를 다시 정해야 한다."

기대 결과:
- 기록 저장
- 관련 회사 후보 추출
- 업무 후보 생성
- 기존 프로젝트와 연결
- 회사 신원이 불확실하면 검토 요청

### Case B — 기존 정보와 연결

과거 기록:
"A회사는 11월 납품을 약속했다."

새 기록:
"A회사와 다시 미팅했다. 납기가 12월로 변경될 가능성이 있다."

기대 결과:
- 동일 회사 연결
- 기존 약속 탐지
- 일정 변경 가능성 표시
- 기존 확정 일정을 자동 삭제하거나 교체하지 않음
- 과거/현재 원본 링크 제공

### Case C — 미팅 기록

음성 파일과 별도 작성 메모를 동일 미팅에 입력한다.

기대 결과:
- 하나의 Meeting ID
- 음성 전사
- 메모 병합
- 결정과 업무 추출
- 원본 참조

### Case D — 중복 저장

동일 기록의 AI 처리가 두 번 실행된다.

기대 결과:
- 중복 Task 생성 방지
- 중복 Memory 생성 방지
- Processing Run 이력 유지

### Case E — 권한 분리

권한이 없는 조직의 메모를 검색한다.

기대 결과:
- SQL 검색에서 접근 차단
- Vector Search에서 접근 차단
- AI 답변에서도 노출 금지

### Case F — 모호한 인물

입력:
"방 사장에게 전달했다."

기대 결과:
- 동일 이름이나 직함을 가진 기존 인물이 있어도 확정하지 않음
- 관련 문맥을 사용한 후보 제시
- 신원 확인이 안 되면 Pending 처리

### Case G — 원본 보존

AI 분석 서비스가 실패한다.

기대 결과:
- 원본 메모는 정상 보존
- Failed 상태 표시
- 재처리 가능
- 중복 데이터 방지

### Case H — 검색 및 근거

질문:
"지난달 A회사가 약속한 것은 무엇이야?"

기대 결과:
- 실제 존재하는 관련 기록 검색
- 기록 시점과 약속 시점 구분
- 답변에 원본 출처 표시
- 관련 기록이 없으면 찾지 못했다고 답변

# 15. 최종 작업 지시

이 문서를 단순 기능 설명서로 취급하지 말고 **실제 Chairman OS 코드베이스에 통합하는 개발 명세**로 사용한다.

개발 순서:

1. 기존 프로젝트 구조를 분석한다.
2. 기존 코드와 신규 기능의 관계를 파악한다.
3. 필요한 DB Migration을 설계한다.
4. API / Service / Repository를 구현한다.
5. AI Processing Engine을 구현한다.
6. Capture 및 Memory UI를 구현한다.
7. 기존 Company / People / Project / Dashboard와 연결한다.
8. 검색 및 AI 질의 기능을 구현한다.
9. 테스트를 작성하고 실행한다.
10. TypeScript / Lint / Build 오류를 확인한다.
11. 기능별 실제 동작을 검증한다.
12. 구현 완료 항목과 남은 항목을 보고한다.

개발 중 기존 기능을 손상하지 않도록 한다.

외부 API 키, 서비스 접근 권한, 브라우저 제약 등으로 완성할 수 없는 부분이 있다면 실제 구현된 것처럼 표시하지 말고, 필요한 설정과 남은 개발 범위를 명확히 기록한다.

먼저 Phase 1을 완성하는 것을 목표로 하며, Phase 2 이후 기능은 확장 가능한 Interface와 Architecture를 준비한다.

최종 결과물:
- 작동하는 Chairman OS 통합 UI
- Database Migration
- AI Processing Engine
- Memory Search
- AI Q&A
- Review Queue
- 기존 Entity 연결
- 기능 테스트
- 필요한 환경변수 설명
- 변경된 파일 목록
- 실행 및 배포 방법

**최종 목표는 사용자가 어떤 메모든 입력만 하면 AI가 기존 Chairman OS의 지식과 연결하고, 미래의 모든 새로운 기록을 통해 점점 더 정확하고 유용해지는 개인 경영 기억 시스템을 만드는 것이다.**

단순히 저장하는 시스템이 아니라, 기록된 정보에 근거하여 대표의 의사결정을 돕는 시스템으로 개발하라.
