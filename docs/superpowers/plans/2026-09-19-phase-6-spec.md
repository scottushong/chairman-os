## 시작 전에 알고 있어야 할 것 (컨트롤러 사전 조사)

### 이미 깔려 있어 새로 만들지 않아도 되는 것

- **자가 가입 → 프로필 연결 경로가 이미 있다.** `0011_user_invitations.sql`이 `auth.users`에
  `on_auth_user_created` 트리거를 걸어 `accept_user_invitation()`을 부른다. 초대가 없으면 아무것도
  하지 않고, 그 계정은 로그인은 되지만 앱을 못 쓴다(Default Deny). 블록 3의 초대 흐름은 맨땅이 아니라
  이 위에 팀 연결만 얹으면 된다. `service_role` 없이 이미 동작한다.
- **`user_invitations` 표와 RLS 정책(`user_invitations_admin`)이 있다.** 초대 발급·회수 화면도 일부 있다.
- **`*_LABEL_KO` 맵이 19개 있다.** 열거값은 이미 한 곳에서 한국어로 번역된다 — i18n의 이음매가
  이미 만들어져 있다는 뜻이다. `*_LABEL_EN`을 짝으로 두는 것이 자연스러운 길이다.

### 손봐야 하는데 지금은 장식인 것

- **헤더 종 아이콘은 숫자가 하드코딩이다.** `header.tsx:25-26`이 `count={12}`, `count={5}`.
  클릭해도 아무 일이 없다. 블록 6이 이것을 실물로 만든다.

### 규모 측정 — P6-2(앱 전체 i18n)

```
한국어가 든 파일        166
한국어가 든 줄(주석 포함) 3,953
주석 제외 근사          1,564
.tsx만(화면 문구 위주)     844
기존 *_LABEL_KO 맵          19
```

즉 화면에 나가는 한국어 문구가 **약 844줄, 100여 개 파일**에 흩어져 있다. 열거값 19종은 이미
중앙화되어 있으므로 그쪽은 짝만 만들면 된다. 나머지가 실제 작업량이다.
**이것만으로 블록 하나가 아니라 Phase 하나에 가깝다** — 계획을 쓸 때 회장에게 다시 한 번
"Phase 6 안에 넣을지, 별도 Phase로 뺄지" 확인한다.

### 가장 위험한 항목

**RLS 재작성이 이 Phase에서 가장 위험하다.** 지금 권한은 `0002_rls.sql`이 역할 + `user_business_access`로
정한다. Phase 6은 여기에 팀 범위를 더한다 — Member는 자기 팀 것만, TeamLead는 팀 전체 + 회장 기안.
`tasks`·`decisions`·`documents`의 핵심 정책을 건드리는 일이고, **실데이터가 든 production에 적용된다.**
계획을 쓸 때:
- 역할별 단언을 `check-migrations.ts`에 먼저 쓰고 정책을 나중에 쓴다(0018에서 효과를 본 방식).
- 의도적 파괴 실험을 각 정책마다 요구한다 — 단언이 실제로 실패할 수 있는지 보이지 않으면 그 단언은
  안심을 팔 뿐이다(0018 1라운드에서 실제로 그랬다).
- `decisions`에 칸을 더하지 않기로 했으므로(P6-3) 기존 행 백필 문제는 없다. 대신 `user_profiles.team_id`가
  **기존 계정 전부 null**로 시작한다 — null인 사람이 무엇을 보는지 정책에 명시해야 한다.

## 블록 (원 지시 그대로)

### 블록 1 — 스키마 (0020)
- `teams`: team_id, business_id, name, name_en, lead_user_id. DY 시드: 영업·생산·경영지원·구매·연구소
- `user_profiles`: team_id, status(active/left), joined_on, left_on
- `approval_rules`: business_id, kind(expense/purchase/leave/hire/contract/task/other),
  team_lead_max_amount(null=무제한), chairman_always(bool), special_condition(text), updated_by
  DY 기본 시드: 전부 팀장 종결. `chairman_always`는 hire·contract만 true.
- **`requests`** (P6-3에 따라 `decisions`가 아닌 새 표): requester_id, team_id, business_id, kind,
  amount, title, body, attachment_url, team_lead_status(pending/approved/rejected),
  chairman_required(bool, 규칙 판정 결과), chairman_status, escalated_manually(bool), bundle_id(취합용)
- `notifications`: user_id, kind, ref_table, ref_id, read_at
- RLS: Member = 자기 팀 tasks/decisions/documents(일반 등급) + 자기 요청.
  TeamLead = 팀 전체 + 회장 기안 + 팀원 등록. Executive/BusinessCEO = 회사 전체, 재무 제한 등급.
  `approval_rules` 편집 = Chairman만. Vault = Chairman + 개별 지정.
- 모든 쓰기 `audit_log`.

### 블록 2 — 결재 규칙 화면 `/settings/approvals` (Chairman)
- 회사 탭 × 유형 행. 팀장 상한 금액 / 회장 항상 / 특수 조건 편집. 저장 즉시 적용.
- **규칙 판정 로직은 한 곳이다** — `lib/approval-rules.ts`와 DB 함수가 같은 판정을 해야 한다.
  팀장 승인 시점에 판정 → `chairman_required` 세팅 → true면 회장 큐, false면 종결.
  (두 구현이 갈리면 화면이 "종결"이라 하고 DB는 "회장 대기"인 상태가 생긴다. 계획에 같은 값을
  내는지 재는 검사를 넣는다.)

### 블록 3 — 직원 등록 `/settings/users` 확장
- 컬럼: 이름·이메일·회사·팀·역할·상태·입사일·언어. 팀별 그룹핑.
- 등록 폼 (Chairman·BusinessCEO: 전 역할 / TeamLead: 자기 팀 Member만)
- 권한 회수(left + revoked_at) / 팀 이동 / 재입사. 전부 `audit_log`.
- 초대: `user_invitations`(0011) 등록 → 직원이 `/login` "처음이세요?"에서 이메일 → Supabase signUp
  → 인증 메일 → 비밀번호 설정 → **기존 트리거**로 프로필·팀 연결. 등록 안 된 이메일은 가입 불가.
- **Supabase Auth 메일 발송 한도를 먼저 확인한다.** 무료 한도가 낮다 — 부족하면 Resend SMTP 연결
  절차를 `docs/OPERATIONS.md`에 쓴다.

### 블록 4 — 직원 홈 `/me` (Member·TeamLead 로그인 후 기본 화면)
- 모바일 우선, 하단 탭바 3개: 내 업무 / 내 요청 / 팀 문서
- 요청 올리기: 유형·금액·제목·내용·첨부링크. **3탭 이내.**
- TeamLead 추가 탭: 팀 요청함(승인·반려, 규칙 자동 판정 표시) / 회장 기안(취합: 여러 건 → 한 묶음,
  또는 "회장 확인 요청" 수동 체크로 규칙 무관 에스컬레이션)
- PWA: manifest·아이콘·홈 화면 추가 안내. **오프라인 캐시 없음**(설치만).

### 블록 5 — 회장 쪽
- "내 결정 사항" = `chairman_required` 또는 `escalated_manually`인 것만.
  카드: "DY 영업팀 · 김OO 팀장 · 3건 취합 · 1,200만 원". 펼치면 원 요청.
  **주의(P6-3):** 이 필터는 `requests`에만 건다. 기존 `decisions`는 지금 규칙대로 계속 보인다.
- "팀 결재 현황" 카드 신설: 이번 주 팀장 종결 건수·금액, 회사·팀별. 읽기 전용 목록 링크.
- 야간 브리핑 `ChairmanContext`에 approvals 요약 추가.
  **주의:** 블록 0이 넣은 `daily-brief.md`의 길이 상한(summary 5문장·items 7개)을 건드리지 않는다.
  늘리면 잘림이 재발한다.

### 블록 6 — 알림
- 헤더 종 아이콘 실제 동작. 요청 접수/승인/반려/회장 도착/회장 결정. 읽음 처리.
- 직원 홈에도 배지.

**계획 단계에서 풀어야 할 문제:** dummy 어댑터는 고정 사용자 하나를 준다. 위 검증은 세션 세 개가
